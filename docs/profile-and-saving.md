# Профіль і збереження

## Референс
ProfileStore (loleris): один «профіль» на гравця, блокування сесії (одночасно лише один сервер тримає дані), автозбереження.
У проєкті через пакет `@rbxts/profile-store` (точна версія в `package.json`), загорнутий у власний адаптер.

## Що беремо
- Сесійне блокування: гравець не може одночасно бути активним на двох серверах, тож дублювання через два сервери неможливе.
- Автозбереження й фінальне збереження при вимкненні сервера: ProfileStore сам підписується на `game:BindToClose`. Перевірено в коді версії 1.0.3 (`init.luau`, рядки ~2074 і ~2082: виставляє `IsClosing`, зберігає всі активні профілі й чекає завершення). Версія в `package.json` закріплена точно, без `^`. Якщо оновлювати пакет, цю перевірку треба повторити.
- Шаблон нового гравця: `createDefaultProfileData()`.

## Що міняємо / додаємо
- Власний конвеєр завантаження (`loadProfileData`): міграція, доповнення, перевірка значень. ProfileStore сам цього не робить.
- Адаптер `ProfileBackend`: вся логіка сесій не залежить від Roblox, тому тестується без Studio.
- Профіль не передається клієнту напряму. Клієнт отримає лише потрібні йому значення окремим кроком, з перевіркою.

## Схема v1
| Поле | Тип | Примітка |
|---|---|---|
| `schemaVersion` | ціле ≥ 1 | Версія схеми. Зараз 1 |
| `level` | ціле 1..`MAX_LEVEL` (50) | |
| `xp` | ціле ≥ 0 | Прогрес усередині поточного рівня |
| `classId` | `warrior` / `mage` / `archer` / порожньо | Обирається один раз |
| `allocatedStats` | 5 цілих ≥ 0 | Витрачені очки. Стартові значення класу додаються при розрахунку |
| `unspentPoints` | ціле ≥ 0 | |
| `gold` | ціле ≥ 0 | |

Похідні значення (HP, мана, урон) **не зберігаються**: вони рахуються, тож зміна формули не ламає старі збереження.

## Як завантажуються дані
1. Гравець заходить: сервер просить сесію `Player_<UserId>`. Без `Steal` (чужу сесію не відбираємо).
2. Сесії немає (сервер завантажений, DataStore недоступний): гравця відключають із поясненням, дані не чіпаються.
3. `loadProfileData`: копія → міграції до поточної версії → доповнення відсутніх полів значеннями за замовчуванням → виправлення некоректних значень → перевірка структури.
4. Дані з **новішою** версією, ніж знає цей сервер, або дані, які не вдалося прочитати: сесія відпускається **без змін**, гравця відключають. Збереження не перезаписується.
5. Інший сервер забрав сесію: гравця відключають.
6. Гравець вийшов: `EndSession` (остаточне збереження). Вихід під час завантаження: сесія одразу відпускається. Швидкий вихід і повторний вхід: стара спроба скасовується.
7. Усі виправлення (наприклад, `level` поза межами) пишуться в лог з `UserId`. Це сигнал про баг або експлойт.

## Як додати нову механіку, не ламаючи збереження
Це головне правило розширення. Три випадки, від найчастішого:

**1. Нове поле зі значенням за замовчуванням** (наприклад, `inventory`, `unlockedAbilityIds`). Версію **не** піднімаємо.
1. Додати поле в `ProfileData` і `createDefaultProfileData()` (`schema.ts`).
2. Додати перевірку структури в `profileDataShape` (`schema.ts`).
3. Додати діапазони й перевірку типів у `sanitize.ts`.
4. Тест у `load-profile-data.test.ts`: старе збереження без поля отримує значення за замовчуванням.

Старі збереження просто отримують значення за замовчуванням під час завантаження. Нові ключі, яких не знає старий сервер, не видаляються.

**2. Змінюємо або видаляємо існуюче поле** (перейменування, інший зміст, інший формат). Версію **піднімаємо**.
1. `CURRENT_SCHEMA_VERSION` + 1 (`schema.ts`).
2. Додати крок у `MIGRATIONS` (`migrations.ts`): `{ from: <стара версія>, apply: (data) => { ... } }`.
3. Тест на цей крок. Тест `realChainCoversEveryVersion` падає, якщо піднято версію без міграції.

Міграція завжди виконується на копії. Якщо вона впала, оригінал зберігається, а гравця відключають.

**3. Новий ідентифікатор** (клас, стат, предмет, здібність). Ідентифікатори стабільні й **не перейменовуються**. Невідомий ідентифікатор у старому збереженні не має ламати завантаження: або його ігнорують, або скидають до безпечного значення (як `classId` у `sanitize.ts`).

**4. Додаємо дозволене значення або піднімаємо ліміт** (новий клас у `CLASS_IDS`, більший максимум у `sanitize.ts`). Версію **піднімаємо** разом із порожньою міграцією (`apply: () => {}`).
Причина: під час оновлення частина серверів ще стара. Старий сервер не знає нового класу чи ліміту, скине значення й **збереже це поверх даних гравця**. Вища версія змушує старий сервер відмовитись від збереження (`future-version`) і не чіпати його.

## Числа (ПЛЕЙСХОЛДЕР)
- Максимуми в `sanitize.ts`: статі й очки ≤ 1000, `xp` і `gold` ≤ 10¹². Це захист від переповнення при пошкоджених даних, а не баланс.

## Roblox і безпека
- Дані гравця пише лише сервер. Клієнт профіль не бачить і не змінює.
- Єдиний код, що відкриває й закриває сесії: `ProfileSessions`.
- `getProfileData(player)` повертає живу таблицю. **Не зберігайте її**: викликайте щоразу перед операцією. Після виходу гравця чи втрати сесії збережену таблицю ще можна змінити, але це вже не потрапить у збереження, а побічні ефекти (наприклад, видана деінде річ) лишаться: це ризик дюпу. Фічі, що переміщують цінність (інвентар, обмін, купівля), перед записом перевіряють, що дані досі активні.
- `loadProfileData` лежить у `shared` лише для тестів. Викликає її й довіряє її результату тільки сервер.
- Повідомлення гравцеві при відключенні не містять його даних.
- У логах лише `UserId`.
- Studio: без увімкненого «Enable Studio Access to API Services» ProfileStore працює на тимчасовому сховищі, дані не зберігаються між запусками.
- Ризик залежності: пакет `@rbxts/profile-store` оновлювався востаннє у листопаді 2024, а оригінал у липні 2025. Усе спілкування з ним іде через `roblox-backend.ts`, тож його можна замінити без зміни решти коду.

## Відновлення гравця (процедура, інструмент ще не зроблено)
DataStore зберігає попередні версії запису (приблизно 30 днів, точний строк перевірте в документації Roblox). Для відновлення:
1. `store:VersionQuery(key, …)` повертає список версій з датами, `NextAsync()` читає потрібну.
2. Прочитати `Data` старої версії **без сесії** (`GetAsync(key, version)` повертає профіль без автозбереження).
3. Перенести потрібні значення в поточний профіль гравця, коли він не в грі, і записати (`SetAsync`).
Інструмент для адміністратора зробимо пізніше окремою задачею. До цього відновлення робить розробник вручну з командного рядка Studio.

## Тести
- `load-profile-data.test.ts`, `migrations.test.ts`: схема, міграції (ланцюжок, збій, майбутня версія), старі збереження, пошкоджені значення (`NaN`, нескінченність, неправильні типи, невідомий клас).
- `profile-sessions.test.ts`: завантаження, відмова, вихід під час завантаження, повторний вхід, дублікати подій, сесію забрав інший сервер, дані з майбутньої версії.
- DataStore безпосередньо headless не перевірити: роботу `roblox-backend.ts` перевіряємо вручну в Studio.

## Відкриті питання
- Як передавати клієнту його власні дані для інтерфейсу (окремий крок: мережа + перевірка, `@rbxts/remo`).
- Інструмент відновлення гравця для адміністратора.
